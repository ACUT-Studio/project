# Стратегія тестування та забезпечення якості (Етап 7)

Документ визначає підхід до верифікації функціональних і нефункціональних вимог настільної гри **AcutStudio** (.NET 10, WPF MVVM, SQLite ADO.NET, xUnit).

---

## 1. Мета та обсяг тестування

Основна мета тестування — гарантувати коректність ігрової логіки (`Acut.Core`), цілісність збереження стану та каталогу в реляційній БД SQLite (`Acut.Data`) та стабільність взаємодії шарів презентації (`acut`) без порушення архітектурних обмежень.

### Об'єкти тестування
1. **Доменна модель та сервіси ядра (`Acut.Core`)**:
   - персонаж гравця (`Player`), характеристики, досвід, рівні, ресурси (`Gold`, `Wood`, `Stone`);
   - економіка міста (`City`, `Building` та підкласи, ліміти забудови, знесення з поверненням $50\%$ витрат);
   - інвентар (`Inventory`, `ItemStack`), спорядження (`Weapon`, `Armor`), крафтинг зілля (`WorkshopBuilding`, `Recipe`), магазин (`Shop`);
   - біржа акцій (`StockMarket`, `Stock`, коливання цін у межах волатильності з нижньою межею $0.01$);
   - покрокова бойова система (`Battle`, стратегії ворогів `IEnemyStrategy`, розрахунок шкоди, захисна стійка, лікування);
   - система прогресу (`SkillTree`, `QuestLog`, `AchievementTracker`, `PlayerStatistics`) та диспетчер подій (`GameEventDispatcher`);
   - життєвий цикл сесії (`GameSession`, `SaveManager`, таблиця дозволених переходів між `GameState`).
2. **Шар доступу до даних (`Acut.Data`)**:
   - ініціалізація схеми (`schema.sql`), початкове наповнення каталогу (`seed.sql`) та послідовні міграції (`migration_002.sql` – `migration_004.sql`) через `PRAGMA user_version`;
   - атомарність збереження стану гри в одній транзакції (`SqliteSaveRepository.Save`);
   - дотримання обмежень цілісності БД (`FOREIGN KEY`, `UNIQUE`, `CHECK`, каскадне видалення `ON DELETE CASCADE`).
3. **Шар представлення (`acut` / `Acut.Ui.Tests`)**:
   - моделі подання (`ViewModel`), команди (`RelayCommand`), валідація введення, реакція на паузу та навігацію.

## 2. Рівні та види тестування

| Рівень тестування | Проєкт | Середовище та ізоляція | Що перевіряється |
|:---|:---|:---|:---|
| **Модульні тести (Unit Tests)** | `Acut.Tests` (`Core/`) | Повністю в пам'яті, **без** WPF і **без** SQLite. Використовуються стаби `FakeCatalog` (`ICatalogRepository`) та `MemoryRepository` (`ISaveRepository`). | Інваріанти доменних класів, формули бою та економіки, переходи станів, обробка подій, крайові умови та винятки (`GameRuleException`, `ArgumentOutOfRangeException`). |
| **Інтеграційні тести (Integration Tests)** | `Acut.Tests` (`Data/`) | Реальний рушій SQLite у режимі спільної пам'яті (`Mode = Memory, Cache = Shared`) через `TestDatabase`. Файл БД користувача `%LocalAppData%\AcutStudio\acut.db` не зачіпається. | Міграції схеми, мапінг ADO.NET (`CatalogMapper`, `SaveMapper`), наскрізний цикл `Save` $\rightarrow$ `Load` (roundtrip), відкат транзакцій при збоях, зовнішні ключі та `CHECK`-обмеження. |
| **Компонентні / UI-тести** | `Acut.Ui.Tests` | STA-потік (`Dispatcher`), DI-контейнер із тестовими сервісами. | Зв'язка `ViewModel` $\leftrightarrow$ `Core`, робота команд, блокування дій під час паузи, відображення шаблонів WPF. |

## 3. Підхід до проектування тестів

- **Патерн AAA (Arrange – Act – Assert)**: чітке розділення підготовки стану, виконання дії та перевірки результату.
- **Аналіз граничних значень (Boundary Value Analysis)**:
  - здоров'я персонажа на межах $0$ та $\text{MaxHealth}$;
  - кількість будівель у місті на межі ліміту ($\text{MaxCityBuildings} = 50$);
  - місткість інвентаря ($\text{InventoryCapacity} = 30$ слотів) під час купівлі та крафтингу;
  - довжина імені персонажа ($0$, $1$, $24$, $25$ символів);
  - мінімальна ціна акції ($\text{MinPrice} = 0.01$) при екстремальному падінні курсу;
  - максимальний рівень будівлі та предмета ($\text{MaxLevel}$).
- **Класи еквівалентності та негативні сценарії**:
  - перевірка відхилення операцій за нестачі будь-якого з трьох ресурсів (`Gold`, `Wood`, `Stone`) без часткового списання;
  - перевірка заборонених переходів між станами гри (`GameState`) та бою (`BattleState`).

## 4. Запуск тестів та критерії успішності

Для запуску всіх модульних та інтеграційних тестів використовується стандартна команда .NET CLI:

```bash
dotnet test acut.slnx
```

### Критерії приймання (Definition of Done для Етапу 7)
1. Рішення `acut.slnx` збирається без помилок (`dotnet build acut.slnx`).
2. Усі модульні тести `Acut.Tests/Core` та інтеграційні тести `Acut.Tests/Data` проходять успішно.
3. Жоден тест у `Acut.Tests` не звертається до файлової БД користувача `%LocalAppData%\AcutStudio\acut.db`.
4. Усі виявлені крайові ситуації покриті регресійними автоматизованими тестами.
